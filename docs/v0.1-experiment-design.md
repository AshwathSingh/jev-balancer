# jev-balancer v0.1 experiment design

## Objective

Determine whether probabilistic semantic estimates of job duration improve
workload scheduling compared with conventional load-only heuristics.

The primary research question is:

> Under heterogeneous workloads, does augmenting a load-aware scheduler with
> probabilistic semantic predictions reduce tail latency and SLA violations
> after accounting for prediction latency and cost?

The initial experiment uses workers with identical capabilities. This isolates
the value of predicting workload size from the separate problem of selecting
between workers with different quality, cost, or specializations.

## Hypothesis

A queue length treats every queued job as equal. When service times vary, a
worker with fewer jobs can still have more work remaining. A semantic predictor
may improve scheduling by estimating the work represented by each queue.

The semantic scheduler is useful only if its prediction improves scheduling
enough to offset its own latency, cost, and errors. A result showing no benefit
is valid and should be reported.

## v0.1 scope

v0.1 is an offline, deterministic simulation package. It will include:

- Synthetic workload generation and JSONL trace replay.
- Identical, non-preemptive workers with one FIFO queue per worker.
- Swappable duration predictors and scheduling policies.
- Conventional, semantic, and oracle baselines.
- Machine-readable benchmark results and per-job decision traces.
- Unit tests for scheduling invariants and deterministic replay.

v0.1 will not include a production proxy, live model execution, worker health
checks, retries, autoscaling, or heterogeneous worker capabilities.

## System model

### Work item

Each work item contains:

| Field | Meaning |
| --- | --- |
| `request_id` | Unique identifier. |
| `arrival_ms` | Simulated arrival time. |
| `payload` | Text available to a semantic predictor. |
| `input_units` | Simple non-semantic feature such as token count. |
| `service_ms` | Observed runtime, hidden from schedulers during routing. |
| `sla_ms` | Optional response-time objective. |

### Worker

Each worker executes one job at a time. Jobs cannot be moved or interrupted
after assignment. At arrival, the scheduler can observe each worker's running
job and queue, but not their true remaining service times.

### Predictor

A predictor returns a probability distribution over duration classes:

```text
short:  0.70
medium: 0.25
long:   0.05
```

Synthetic traces declare duration classes from configured service-time range
thirds. Representative runtimes and prediction parameters are learned from a
training split. Evaluation uses a later label-safe chronological holdout to
prevent unavailable runtimes from entering training.

For a job `j`, its expected service time is:

```text
E[service(j)] = sum(P(class | j) * mean_service_ms(class))
```

The prediction interface must be provider-neutral. v0.1 uses deterministic
mock predictors; a Jev adapter is deferred until the benchmark is trustworthy.

## Scheduling policies

Every workload trace will be replayed through the same policies:

1. **Round robin**: assign workers in a fixed cycle.
2. **Least jobs**: choose the worker with the fewest running and queued jobs.
3. **Mean-work**: estimate every job with the global historical mean.
4. **Input regression**: estimate duration from `input_units` without semantics.
5. **Semantic work**: estimate duration from semantic class probabilities.
6. **Semantic quantile/CVaR**: reserve work using an upper quantile, upper-tail
   mean, or expected/CVaR blend.
7. **Semantic entropy fallback**: move toward input regression as the semantic
   distribution becomes less concentrated.
8. **Oracle work**: use true service times in the same greedy routing rule as a
   non-deployable perfect-information comparator, not a global optimum.

The work-aware policies choose the worker with the lowest estimated remaining
backlog. After assignment, the new job's estimated duration is added to that
worker's backlog. Ties are resolved by stable worker identifier so runs are
reproducible.

## Experimental regimes

Synthetic traces will vary one factor at a time:

- Worker utilization: low, moderate, and near saturation.
- Service-time variance: uniform through heavy-tailed.
- Arrival pattern: steady and bursty.
- Predictor quality: accurate through uninformative.
- Predictor overhead: zero through greater than the expected scheduling gain.

All policies will receive identical jobs, arrival times, worker counts, and
random seeds.

## Metrics

Primary metrics:

- p50, p95, and p99 queue wait and end-to-end response time.
- SLA violation rate.
- Throughput and total makespan.

Diagnostic metrics:

- Per-worker utilization and utilization imbalance.
- Prediction error and probability calibration.
- Scheduler and predictor overhead.
- Routing decisions that differ from the oracle.

End-to-end response time includes prediction overhead. Results must not report
latency improvements while excluding the cost of producing the prediction.

## Evaluation rule

The semantic approach earns further live experimentation if it reduces p95
end-to-end latency or SLA violations by at least 10% against the strongest
non-semantic policy in at least two high-variance, moderate-or-higher load
regimes, without reducing throughput by more than 2%.

This threshold is a project decision, not a claim of statistical significance.
The report must include all regimes, including neutral and negative results.

## Correctness requirements

Every simulation run must satisfy:

- Each submitted job is assigned and completed exactly once.
- A worker never executes overlapping jobs.
- `arrival_ms <= start_ms <= finish_ms` for every job.
- Repeated runs with the same trace, policy, and seed are identical.
- Policies cannot read `service_ms` except for the oracle baseline.

## Planned package boundary

```text
src/jev_balancer/
  models.py
  scheduler.py
  predictors/
  policies/
  simulation/
  metrics.py
  cli.py
tests/
```

The public API will accept a work item plus worker snapshots and return a
routing decision with the chosen worker, estimated backlog, predictor output,
and timing diagnostics. Simulation, predictor, and policy interfaces will stay
independent so later versions can add Jev and a live gateway without changing
the scheduling core.

## Delivery sequence

1. Package skeleton and domain models.
2. Deterministic simulator and correctness tests.
3. Conventional policies and benchmark reporting.
4. Mock semantic predictor, semantic policy, and signal-quality sweeps.
5. Uncertainty-aware policies and multi-seed experimental matrix.
6. Jev adapter and shadow-mode experiments on labeled traces.
7. Optional live gateway after offline results justify it.
